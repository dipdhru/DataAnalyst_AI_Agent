DataAnalyst Agent

How it works

You ask a database a business question in plain English. The agent writes SQL, runs it read-only, checks it, and gives back the number together with the query that produced it. This page walks through every step and shows how the project measures whether the answers are right.

The big picture

There are three parts. A catalog learns the database before any question is asked. An agent answers the question with a small set of tools. A checking layer makes sure the SQL is safe, runs it again, and, if you ask for it, compares it with a second independent attempt.

Everything the agent runs, including the catalog's profiling queries, goes through the same guard and the same read-only connection.

One question, step by step

Take "What is our total revenue?" on the Olist e-commerce data (about 100,000 Brazilian orders, 11 tables). It looks easy, and it's a good example of why the project exists.

  1. The prompt is built. The model gets the list of tables, the business definitions for this data source, and any memory that matches the question (an answer you marked correct before, a glossary entry). The prompt stays the same for every question on a source, so the provider can cache it.
  2. The agent explores. It may call describe_table("order_items") to see columns, nulls and sample values, then try a query with run_sql to look at real rows. Each result comes back trimmed to 50 rows so the model's context doesn't fill up.
  3. It applies the definition. The definitions say revenue is SUM(order_items.price) over valid orders (not canceled or unavailable), and that payment_value is not revenue, because it also includes freight, interest and vouchers.
  4. It submits. submit_answer carries a one-sentence answer, the final SQL, and whether the question was answerable at all.
  5. The SQL is run again. The submitted SQL is executed through the guard before the answer is accepted. If it fails, the error goes back to the model to fix. The number you see is always the output of the SQL you see, never a number the model typed.
  6. The answer is shown with the SQL, the result table, a chart picked from the shape of the result (a single number, a line over time or bars), and, with "Double-check answers" on, a trust label.
Without definitions 
SELECT SUM(payment_value)
FROM order_payments;

SELECT ROUND(SUM(oi.price), 2)
FROM order_items oi
JOIN orders o USING (order_id)
WHERE o.order_status NOT IN

13,494,400.74: the business's answer

The real danger in text-to-SQL is not SQL that crashes. It's SQL that runs and returns a believable but wrong number. Most of this project's design is about that.

The catalog: learning the database first

Before any question, the catalog reads the schema and profiles every column: share of nulls, number of distinct values, min and max, and a few sample values. The profiling SQL is portable, built with sqlglot and rendered in each database's dialect, so the same code runs on SQLite and Postgres.

Inferred joins

Olist declares no foreign keys. The catalog infers joins from matching column names where one side is a key (all values distinct and non-null), so the agent knows orders.customer_id = customers.customer_id.

Descriptions from three places

Yours (typed in the Catalog view), imported ones (for example BIRD's column CSVs), or ones the model writes for gaps. Yours always win and survive every refresh.

Stored locally

Catalogs live in state/app.db (SQLite), next to memory and saved conversations.

Business definitions: the semantic layer

metrics.yaml holds what words mean for this business. A few of the Olist ones:

TermMeaningThe trap it prevents
revenueSUM(order_items.price) over valid ordersUsing payment_value, adding freight
customerA person: customers.customer_unique_idcustomer_id is per order, so 99,441 "customers" instead of 96,096
late_deliveryDelivered on a later day than estimatedComparing timestamps marks same-day deliveries late
active_sellerAt least one item in a valid orderCounting the whole sellers table

A database can tell a model which columns exist. It can't tell it which of two valid queries the business means. Definitions fill that gap, and the experiment below measures how much it matters.

Safety: read-only in two layers

The agent writes its own SQL, so the system assumes some of it will be wrong or hostile and blocks writes in two independent places.

Neither layer is trusted alone. Tests deliberately skip the guard to prove the connection still refuses writes.

Every query in the codebase, from the agent, the profiler or the API, goes through one method, Connector.run_query, which applies both. In the public demo, a visitor's Postgres address is also vetted (public IPs only, TLS required), so the app can't be used to reach private networks.

The trust check: knowing when not to trust it

A wrong answer looks exactly like a right one. With Double-check answers on, the agent answers the question a second time, told to work it out from scratch and to prefer a different way of writing the query. Then the two results are compared.

✅ Double-checked

Both attempts returned the same result. Not proof, because both can make the same mistake, but a useful signal.

⚠️ Double-check this

The attempts disagree. Look at the SQL before you use the number.

On the BIRD benchmark sample, answers labelled double-checked were right 9 of 11 times (82%), against 11 of 15 (73%) for all answers. That's an early number from a small sample. The check doubles model calls, so it's off by default.

Memory: only you write it

Three kinds of memory are recalled into each question by word overlap (TF-IDF):

  • Verified queries. Answers you marked correct, reused as worked examples.
  • Glossary. Your words for things ("GMV means revenue").
  • Corrections. "That was wrong because…", so the mistake isn't repeated.

The agent reads memory but never writes it. Only the buttons in the UI do. A model that saves its own conclusions can turn one wrong answer into a permanent one. After a catalog refresh, verified queries are checked again so stale ones drop out. Evaluations run without memory, so scores stay comparable over time.

Measuring it

Golden questions

30 Olist business questions in evals/golden.yaml, across revenue, orders, delivery, customers, sellers, reviews, payments, marketing and 2 questions the data can't answer. Each has hand-written SQL. Expected answers are computed from that SQL by a script, never typed in, and a question only counts once its owner has reviewed and approved it.

Scoring

An answer passes if its result table matches the golden one: every expected column is found among the returned ones, numbers within a small tolerance, row order checked only when the golden SQL sorts. For unanswerable questions, declining is the right answer.

Public benchmark

BIRD Mini-Dev, the standard text-to-SQL benchmark, scored by execution accuracy on a fixed sample. Long runs save after every question and resume the next day, so free-tier daily limits don't lose work.

Agent tests never call a real model. A scripted fake model plays back replies, so the test suite (300+ tests) runs offline in about 20 seconds.

The A/B/C experiment

Which parts of the design actually help? To find out, the same model answers the same 30 questions in three stripped-down setups. Each makes one attempt, without the tool loop, so only one thing changes at each step.

Retrieval picks about 4 of the 11 tables per question by TF-IDF similarity to the question, plus any table a retrieved definition's SQL mentions.

What it shows

Help matters: +26.7 points

B fixed 8 questions A got wrong, mostly revenue, customers and sellers. A's failures were all SQL that ran and returned the wrong number. Without definitions, it guessed what "revenue" or "customer" means.

Correction never ran

No SQL failed, so C behaved exactly like B on every question. Correction only fixes SQL that crashes, and this model's mistakes are SQL that runs.

Retrieval's price

B's 3 misses are exactly the 3 questions where retrieval left out a needed table. Each time, the model declined instead of guessing. Shown the whole schema, A got one of them right.

Read these as early numbers. One model, one run, 30 questions, where one question is worth 3.3 points. The golden questions were still being reviewed. And A and B differ in two ways at once (fewer tables and definitions), so the +26.7 can't yet be split between them. Next: a whole-schema-plus-definitions setup to separate the two, more questions, more models and repeated runs.

Limits, said plainly

  • Small samples so far: 30 golden questions and 20 BIRD questions, one run per setup.
  • The trust check can't catch a mistake both attempts make the same way.
  • Memory recall matches words, not meaning: "sales" won't find a note about "revenue".
  • No login, PII masking or audit log yet (planned). Column samples store raw values.
  • SQL databases only. MongoDB is a later phase.
